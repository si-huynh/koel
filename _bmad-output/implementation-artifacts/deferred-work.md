### Session-lifecycle / concurrency cluster (deferred to Epic 6 `KoelChatController`, story 6-1)

The maintainer deferred this entire cluster on 2026-05-30: `ChatSession` has **no reliable "a run is in flight" predicate** (`_sub`/`_completer` are never nulled on completion), so every off-happy-path lifecycle transition misbehaves. All 4 ACs of 2.14 pass; these are robustness gaps no AC exercises. Session lifecycle/concurrency is architecturally owned by `KoelChatController` (Epic 6, story `6-1`) — fix the cluster there with a single in-flight state machine (track + null `_sub`/`_completer`; define the concurrent-`send` contract; have `cancel`/`clear`/`dispose` cancel the live subscription before mutating state). (Source: Blind Hunter + Edge Case Hunter, code review of story 2-14.)

- **Concurrent / re-entrant `send()` corrupts the session** — `packages/koel_core/lib/src/client/chat_session.dart:496-552`. A second `send()` before the first run finishes overwrites `_completer` (the first `send`'s future then resolves on the *second* run's completion, or hangs) and overwrites `_sub` **without cancelling the prior subscription** — two `reducingApplyStage` folds race into one `_state`, and the first run becomes uncancellable. CRITICAL severity but consumer-misuse-adjacent (a single `await session.send(...)` serializes naturally; the gap is an un-awaited double-`send`, e.g. a UI double-tap). The contract is genuinely ambiguous (reject-with-`StateError` / cancel-prior-then-start / queue) — decide it in `KoelChatController`.
- **`_sub`/`_completer` never nulled on completion — no in-flight predicate** — `chat_session.dart:533,594-597`. After `onDone`/`onError`, `_sub` still references the drained subscription and `_completer` the settled completer; the session cannot answer "is a run in flight?". This is the cluster's root cause — the other four items all depend on a reliable predicate.
- **`clear()` does not cancel the in-flight run** — `chat_session.dart:565-568`. `_emit(const ChatState())` resets to idle, but the live run's `reducingApplyStage` (seeded with `initial: _state` at send-time) keeps folding onto its captured copy; the next event's `onState`→`_emit` resurrects the cleared conversation. Contrast `cancel()`, which does `_sub?.cancel()`.
- **`cancel()` after a run already finished flips `idle`→`cancelled`** — `chat_session.dart:558-562`. Unconditional `_emit(_state.copyWith(phase: RunPhase.cancelled))` broadcasts a wrong phase over a completed conversation (e.g. a cancel button the UI didn't disable in time). Should no-op when no run is in flight.
- **`send()` after `dispose()` silently half-runs** — `chat_session.dart:496`. The session is already removed from `_client._sessions` (so `client.dispose()` can never cancel the new run → it leaks), yet `send` still drives the full agent+pipeline and fires client subscribers; `_emit` is silently dropped (closed-controller guard). Should reject with `StateError` (use-after-dispose idiom).

# Story 4.9: Connection lifecycle hooks

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **Dev agent:** this is **Story 4.9 of Epic 4** (HTTP transport, `koel_http`). It makes the two remaining `HttpAgent` lifecycle callbacks — `onConnect` and `onDisconnect` — *do something*: fire `onConnect` when the SSE response headers arrive and `onDisconnect` exactly once when that connection's stream ends (graceful, error, or consumer cancel), so DevTools (Epic 8) and custom observers get transport-level visibility (FR-B6). The third callback, **`onReconnectAttempt`, is already fully wired** through `RetryInterceptor.forAgent` (Story 4.4) — you do **not** rebuild it; you verify it and route it through the new lifecycle holder unchanged. It touches `.dart` files and the transport seam, so **invoke `/agent-flutter-engineer` before producing any code** (per [CLAUDE.md](CLAUDE.md)). `packages/koel_http/` already ships `SseParser` (4.1), `HttpAgent` + the transport seam + `_TransportTerminal` (4.2), the `abortOnCancel` watchdog (4.3), the six interceptors (4.4–4.7), and chunk synthesis (4.8). **The single most important fact: `onConnect`/`onDisconnect` are currently DROPPED on the floor — the 4.2 ctor accepts them but the initializer list never stores them.** Ten things are load-bearing; the first five sink a naïve reading of the AC:
>
> 1. **`onConnect`/`onDisconnect` are currently DROPPED — you must add the fields and fire them.** The 4.2 ctor *accepts* `void Function()? onConnect` and `void Function(Object)? onDisconnect` but the initializer list only assigns `_client`/`_retry`/`_onReconnectAttempt`/`_interceptors` ([http_agent.dart:78-92](packages/koel_http/lib/src/http_agent.dart)). The ctor dartdoc says so explicitly: *"[onConnect]/[onDisconnect] … owned by Story 4.9 … accepted now so the constructor is a single one-way door, consumed when that story lands"* ([http_agent.dart:75-77](packages/koel_http/lib/src/http_agent.dart)). **This is that story.** Store them (bundled — trap #3), fire them, and delete that deferral sentence. This is the exact same dropped-param shape Story 4.8 fixed for `synthesizeChunks` (trap #5 there). [Source: http_agent.dart:75-92; 4-8 trap #5]
> 2. **`onReconnectAttempt` already works — do NOT touch its behavior.** `RetryInterceptor.forAgent(onReconnectAttempt: …)` ([retry_interceptor.dart:70-82,164-170](packages/koel_http/lib/src/interceptors/retry_interceptor.dart)) already fires it once per scheduled retry with the 1-based attempt index and the jittered delay, and `HttpAgent.run` already passes `_onReconnectAttempt` into it ([http_agent.dart:128-139](packages/koel_http/lib/src/http_agent.dart)). AC2's `onReconnectAttempt` assertions are a **regression check on existing wiring**, not new code. The only change permitted here is *plumbing the same callback through the new lifecycle holder* (trap #3) — the value passed to `RetryInterceptor.forAgent` must be behaviorally identical (re-run [retry_interceptor_test.dart](packages/koel_http/test/retry_interceptor_test.dart) green to prove it). [Source: retry_interceptor.dart:70-82,164-170; http_agent.dart:128-139; 4-8 "OUT OF SCOPE: onReconnectAttempt is already wired — do not extend"]
> 3. **The hooks fire from INSIDE `_TransportTerminal.run` (innermost, per-connection) — the same placement chunk synthesis uses (4.8 trap #4).** `RetryInterceptor` is the outermost interceptor and **re-runs the terminal per attempt** ([http_agent.dart:124-144](packages/koel_http/lib/src/http_agent.dart)). Because each reconnect re-enters the terminal, putting `onConnect`/`onDisconnect` in the terminal makes them fire **once per physical connection automatically** — which is exactly what AC2 demands ("`onConnect` fires once per successful connection (3 total)"). Put them anywhere above the chain and you'd fire once for the whole logical run, failing AC2. Bundle the three callbacks into one `ConnectionLifecycle` value (new `lifecycle.dart`, trap #6), pass it into `_TransportTerminal`, and route its `onReconnectAttempt` field to `RetryInterceptor.forAgent`. [Source: http_agent.dart:124-144,153-156; 4-8 trap #4]
> 4. **`onConnect` = response-headers-received, status-agnostic. `onDisconnect` = stream-end, exactly once, paired.** Resolve the firing points precisely (these are RESOLVED below — implement, don't re-litigate):
>    - **`onConnect` fires the instant `Transport().connect()` returns** a `TransportResponse` ([http_agent.dart:191-202](packages/koel_http/lib/src/http_agent.dart)) — headers are in hand. It fires for **any** received response **including a non-2xx** (a 503 *is* a connected-then-rejected HTTP exchange — "transport-level visibility", FR-B6). A pre-headers failure (connection-refused / TLS / connect-timeout — `connect()` *throws*, [io_transport.dart:54-59](packages/koel_http/lib/src/transport/io_transport.dart)) fires **neither** hook: nothing connected, so nothing to disconnect.
>    - **`onDisconnect` fires exactly once when that connection ends** — graceful `onDone` (cause `null`), stream error (cause = the error), the non-2xx throw path (cause = the `TransportError`), and consumer **cancel** (cause `null` — trap #5). Every `onConnect` is matched by exactly one `onDisconnect`; an idempotent once-guard in the holder makes double-firing impossible. [Source: io_transport.dart:20-60; http_agent.dart:191-242]
> 5. **Cancel must fire `onDisconnect(null)` — and the `<50 ms` abort budget must still hold (NFR-8).** A consumer `cancel()` mid-stream is a real disconnect; fire `onDisconnect(null)` (cancel is clean, not an error) so the hooks stay paired and DevTools shows accurate teardown. The trap: `abortOnCancel` deliberately **strands** the consumer cancel — it does not thread it through the inner `async*`, and **does not await** the teardown on the return path ([cancellation.dart:50-83](packages/koel_http/lib/src/connection/cancellation.dart)). So `onDisconnect`-on-cancel must hang off a boundary that *does* observe cancel: wrap the event stream with a `StreamController` whose `onCancel` fires the holder's once-guarded disconnect (same shape as `abortOnCancel` itself), placed **inside** `abortOnCancel` so the abort still fires first and independently. Re-run [cancellation_test.dart](packages/koel_http/test/cancellation_test.dart) with the hooks attached to prove `<50 ms` abort is unaffected (the disconnect callback is fire-and-forget — trap #7 — so a slow/throwing observer can't stall the budget). [Source: cancellation.dart:50-102; NFR-8]
> 6. **`lifecycle.dart` is the architecturally-mandated home — and it stays INTERNAL (no barrel export).** The architecture source tree names [`connection/lifecycle.dart # F-B6 onConnect/onDisconnect hooks`](architecture.md#L843-844) explicitly. Create it with a `final class ConnectionLifecycle` that (a) holds the three callbacks, (b) exposes `connected()` (fires `onConnect`, once-guarded per connection) and a stream wrapper `track(Stream<AgUiEvent>)` that fires `onDisconnect` once on done/error/cancel. Mark it `@internal` and **do not export it from [koel_http.dart](packages/koel_http/lib/koel_http.dart)** — the public surface is the `HttpAgent` ctor callbacks (AC3: DevTools subscribes via those closures, *no private state*). A new public symbol would be an unneeded 1.x surface; the transport seam ([transport.dart](packages/koel_http/lib/src/transport/transport.dart)) is the precedent for "internal `src/` type, not barrel-exported". [Source: architecture.md:843-844; transport.dart; AC3]
> 7. **Lifecycle callbacks are fire-and-forget — a throwing observer must not abort or hang the run.** `RetryInterceptor` already wraps `_onReconnectAttempt?.call(...)` in `try/catch { /* swallow */ }` ([retry_interceptor.dart:164-170](packages/koel_http/lib/src/interceptors/retry_interceptor.dart)) precisely because telemetry must never break a recoverable run. Mirror that: `onConnect`/`onDisconnect` invocations in the holder are each wrapped in `try/catch` that swallows (the run proceeds regardless). An uncaught throw from `onDisconnect` on the cancel path would escape to the zone and could strand the consumer. [Source: retry_interceptor.dart:164-170; 4-4 throwing-observer precedent]
> 8. **`onDisconnect`'s parameter is `Object?` (nullable), not the Addendum-A.2 `Object`.** Addendum A.2 froze the placeholder as `void Function(Object)?` ([addendum.md:299](_bmad-output/planning-artifacts/prds/prd-koel-2026-05-27/addendum.md)), but **the epic AC specifies `Object?`** ("with the `Object?` cause if error" — [epic-4:226](_bmad-output/planning-artifacts/epics/epic-4-http-transport-koelhttp.md)) because a *graceful* close has **no** cause. The story AC is the contract: widen the ctor param to `void Function(Object? cause)?`. This is a deliberate, AC-forced refinement of the unused A.2 placeholder (no published `dart_apitool` baseline exists yet — Story 9.3 — so no API-diff gate fires); flag it in the Change Log as an A.2 erratum to reconcile in Story 9-7. This is the **one** public-ctor-surface touch in the story; everything else is internal. [Source: addendum.md:299; epic-4:226; 4-8 barrel-erratum precedent]
> 9. **NO logging in `lifecycle.dart`.** Architecture §4 lists `Level.INFO: connection lifecycle (open, close, reconnect attempt)` ([architecture.md:589](packages/../architecture.md)), but that is the **`LoggingInterceptor`'s** domain (Story 4.6) and/or a consumer-attached logging closure — **not** this story. 4.9 ships *pure callbacks*; adding `package:logging` calls here would double-log connection events and creep scope. (No `print` anywhere, per architecture §4.) [Source: architecture.md:589; 4-6 LoggingInterceptor scope]
> 10. **No new dependency, no new freezed type, no codegen, NO finalization gates.** `ConnectionLifecycle` is a plain `final class` (callbacks + a `StreamController` wrapper) — **not** freezed (no value-equality need; it holds closures, which are reference-typed). `melos run build` regenerates nothing. As a Flutter/Dart developer,

so that DevTools (Epic 8) and custom observers attach to connection events per FR-B6.

## Acceptance Criteria

Verbatim from [epic-4 Story 4.9](_bmad-output/planning-artifacts/epics/epic-4-http-transport-koelhttp.md) (lines 215-236):

1. **Given** an `HttpAgent` constructed with all three callbacks, **When** a run successfully connects, executes, and finishes, **Then** `onConnect` fires exactly once on response-headers-received, **And** `onDisconnect` fires exactly once on stream close (graceful or error) with the `Object?` cause if error, **And** `onReconnectAttempt` does not fire (no retry occurred).

2. **Given** a transient failure triggering 2 retries before success, **When** the run executes, **Then** `onConnect` fires once per successful connection (3 total), **And** `onReconnectAttempt(attempt, delay)` fires twice with the computed delays.

3. **Given** these hooks attached to the lifecycle subsystem at `koel_http/lib/src/connection/lifecycle.dart`, **When** Epic 8 wires `DevToolsObserver`, **Then** the observer subscribes to these hooks without needing access to private state.

> **AC clarifications (RESOLVED — do not re-litigate, implement):**
>
> - **AC1 "response-headers-received".** `onConnect` fires the instant `Transport().connect()` returns a `TransportResponse` ([http_agent.dart:191-202](packages/koel_http/lib/src/http_agent.dart)) — *before* the non-2xx status check, status-agnostic (trap #4). A run that connects, streams, and finishes cleanly fires `onConnect` once and `onDisconnect(null)` once. [Source: http_agent.dart:191-222]
> - **AC1 "graceful or error" + `Object?`.** `onDisconnect` fires on **every** end of a connected stream: graceful `onDone` → cause `null`; mid-stream error (e.g. `readTimeout` → `TimeoutException`) → cause = the error; non-2xx → cause = the synthesized `TransportError`; consumer cancel → cause `null` (trap #5). > - **AC2 "transient failure" must be a POST-headers failure.** For `onConnect` to fire "3 total", each of the 3 attempts must *receive headers*. A connection-refused (pre-headers) is retryable but fires **no** `onConnect` (trap #4) — so the test's flaky server must return a **non-2xx** (e.g. HTTP 503) for the first two requests then 200, *not* refuse the connection. The 503 path: `onConnect` → non-2xx `TransportError` (retryable per the default `_retryTransient` predicate, [retry_interceptor.dart:250](packages/koel_http/lib/src/interceptors/retry_interceptor.dart)) → `onDisconnect(cause)` → `onReconnectAttempt(n, delay)` → reconnect. Sequence over the 2-retry run: `onConnect`×3, `onDisconnect`×3 (2 with `TransportError` cause, 1 `null`), `onReconnectAttempt`×2. [Source: retry_interceptor.dart:108-244,250; trap #2/#3/#4]
> - **AC2 needs `retry:` set.** `onReconnectAttempt` only flows when a `RetryInterceptor` is in the chain — `HttpAgent` auto-prepends one **only when `retry:` is non-null** ([http_agent.dart:123-139](packages/koel_http/lib/src/http_agent.dart)). [Source: http_agent.dart:123-139; reconnect_policy.dart:16-37]

No event-bus, no observer registry, no public lifecycle stream — that is YAGNI for 4.9 (the network panel wiring is Epic 8's job, built on these closures). The AC3 "test" is an assertion that closures passed to the ctor are honored — already proven by AC1/AC2; add one explicit doc-style test if it clarifies intent. [Source: architecture.md:118-120,843-844; trap #6]
> - **OUT OF SCOPE (RESOLVED — do NOT build):** rebuilding/extending `onReconnectAttempt` (already wired — trap #2); an explicit `connect()`/`disconnect()` method pair or a `MetaEvent` connection-state channel (the [review-api §3.1 "asymmetric lifecycle"](_bmad-output/planning-artifacts/prds/prd-koel-2026-05-27/review-api-and-completeness.md) note proposed alternatives — the FR-B6 callback design is what shipped in A.2 and the epic; do **not** redesign here); `HttpAgentConfig` ctor-param consolidation ([review-api §"10 params"](_bmad-output/planning-artifacts/prds/prd-koel-2026-05-27/review-api-and-completeness.md) — a future refactor, not 4.9); any `package:logging` output (trap #9); web transport + `package:web` + `sse_parse_bench` (Story 4.10); the ≥90% coverage gate + member-doc `analysis_options.yaml` (epic-sealing Story 4.10 — write full dartdoc anyway); any change to `chunksStage`, the pipeline order, or `RetryInterceptor`'s retry behavior. ## Dev Notes

### What this story is, in one paragraph

The two parked `HttpAgent` lifecycle callbacks finally do their job. `onConnect` fires when the SSE response headers arrive (status-agnostic — a 503 connected, then failed); `onDisconnect` fires exactly once when that physical connection's stream ends — graceful (`null`), error (the cause), non-2xx (the `TransportError`), or consumer cancel (`null`). The third callback, `onReconnectAttempt`, is **already** wired through `RetryInterceptor.forAgent` (4.4) and is only *re-plumbed* through a new `ConnectionLifecycle` holder, behaviorally unchanged. The new `connection/lifecycle.dart` (architecturally mandated, `@internal`, not barrel-exported) bundles the three callbacks and provides a once-guarded `connected()` + a cancel-safe `track(Stream)` wrapper. The hooks fire from **inside `_TransportTerminal.run`** — the innermost, per-connection seam beneath `RetryInterceptor` — so retries fire them per attempt automatically (AC2's "3 total"). Scope is **one NEW file + one MODIFY (`http_agent.dart`) + one NEW test + one MODIFY test**. No new dependency, no freezed type, no `koel_core` change, no finalization gates.

### Where the hooks fire (the placement that makes AC2 free)

```
HttpAgent.run ─► InterceptorChain[ RetryInterceptor(forAgent, onReconnectAttempt) ─► …user… ─► _TransportTerminal ]
                                          │ re-runs the terminal per attempt                        │
                                          │                                                         ▼
   per scheduled retry: onReconnectAttempt(n, delay)          _TransportTerminal.run (per physical connection):
                                                                connect() ──► lifecycle.connected()   = onConnect (headers in)
                                                                if non-2xx ─► lifecycle.disconnect(err) = onDisconnect(cause); throw
                                                                else ──► abortOnCancel( lifecycle.track(events), abort )
                                                                                            └─ onDone→onDisconnect(null)
                                                                                            └─ onError→onDisconnect(error)
                                                                                            └─ onCancel→onDisconnect(null)
```

- **`onConnect`/`onDisconnect` live in the terminal** (innermost) → fire **once per physical connection**. `RetryInterceptor` re-enters the terminal each attempt, so a 2-retry run yields 3× each — AC2 with zero counting logic. [Source: http_agent.dart:124-144; trap #3]
- **`onReconnectAttempt` lives in `RetryInterceptor`** (outermost) → fires once per *scheduled retry*, between a failed connection's `onDisconnect` and the next `onConnect`. Already built (4.4); 4.9 only routes the same callback through the holder. [Source: retry_interceptor.dart:155-176; trap #2]
- **The pairing invariant** — `#onConnect == #onDisconnect` — holds because both sit on the same per-connection seam, gated once each. A pre-headers failure (refused/TLS/connect-timeout, `connect()` throws) fires neither; it surfaces only via `onReconnectAttempt` (if retrying) or the terminal `RunErrorEvent`. [Source: io_transport.dart:54-59; trap #4]

### Cancel-safety: why `track` mirrors `abortOnCancel` and why both are needed (RESOLVED — trap #5)

`abortOnCancel` ([cancellation.dart:50-83](packages/koel_http/lib/src/connection/cancellation.dart)) wraps the event stream so a consumer `cancel()` fires `response.abort()` within `<50 ms` (NFR-8) **without awaiting** the teardown — a misbehaving client must not hang `cancel()`. Because it strands the cancel, a `try/finally` inside the terminal's `async*` would **not** run promptly on cancel. So `onDisconnect`-on-cancel hangs off `lifecycle.track`, a second `StreamController` wrapper **inside** `abortOnCancel` whose `onCancel` fires the once-guarded `_disconnect(null)`. Ordering on consumer cancel: `abortOnCancel.onCancel` fires `abort()` (TCP teardown, budget met) and cancels its upstream → that cancel reaches `track`'s subscription → `track.onCancel` fires `onDisconnect(null)`. The disconnect callback is fire-and-forget (trap #7), so even a slow/throwing observer cannot extend the `<50 ms` budget — which the extended `cancellation_test` proves. The once-guard means a near-simultaneous `onDone`+`onCancel` (stream completes as consumer cancels) still fires `onDisconnect` exactly once. [Source: cancellation.dart:50-102; NFR-8; trap #5/#7]

### `onDisconnect` cause matrix (RESOLVED — trap #4)

| Connection end | `onConnect`? | `onDisconnect` cause |
| --- | --- | --- |
| Graceful finish (`RUN_FINISHED`, stream `onDone`) | yes | `null` |
| Mid-stream error (`readTimeout` → `TimeoutException`, abrupt close) | yes | the stream error |
| Non-2xx response (e.g. 503/500) | yes | the synthesized `TransportError(transportClosed, statusCode:)` |
| Consumer `cancel()` mid-stream | yes | `null` |
| Pre-headers failure (refused / TLS / connect-timeout — `connect()` throws) | **no** | **no `onDisconnect`** (never connected) |

[Source: http_agent.dart:191-242; io_transport.dart:54-59; trap #4/#5]

### Design decisions (RESOLVED — AC/architecture-forced, not open)

1. **Hooks fire from inside `_TransportTerminal.run` (per-connection, beneath `RetryInterceptor`)** → retries fire them per attempt automatically (AC2 "3 total"). [trap #3]
2. **`onConnect` = `connect()`-returned/headers-received, status-agnostic** (fires for non-2xx too); a pre-headers failure fires neither hook. [trap #4]
3. **`onDisconnect` fires exactly once per connected stream** — graceful `null`, error cause, non-2xx `TransportError`, cancel `null` — via a once-guard. [trap #4/#5]
4. **Cancel fires `onDisconnect(null)` from a `track` wrapper inside `abortOnCancel`; the `<50 ms` budget is unaffected** (fire-and-forget). [trap #5/#7]
5. **`onDisconnect` param is `Object?`** (epic AC overrides A.2's `Object` placeholder); the one public-ctor refinement. [trap #8]
6. **`onReconnectAttempt` is reused unchanged**, only re-plumbed through `ConnectionLifecycle`; `RetryInterceptor` behavior is frozen. [trap #2]
7. **`ConnectionLifecycle` is `@internal`, not barrel-exported; DevTools subscribes via the public ctor closures** (AC3 — no private state). [trap #6]
8. **No logging, no new dependency, no freezed type, no `koel_core` change, no finalization gates.** [trap #9/#10]

These are baked in — implement them; no confirmation gate (except the single `Object`→`Object?` A.2-erratum judgment surfaced to the user separately).

- [x] [Review][Patch] `track().onError` arm (mid-stream stream-error → `onDisconnect(cause)`) is untested [packages/koel_http/test/lifecycle_test.dart] — **FIXED**: added `_idleServer` + test "AC1: a mid-stream error fires onDisconnect once with the stream error as cause (track onError arm)" (idle past `readTimeout` → `TimeoutException` through `track.onError`); asserts `onConnect`×1, `onDisconnect`×1 with `isA<TimeoutException>()` cause, and `RunErrorEvent(transportTimeout)` still forwarded. Also tightened the throwing-observer test to assert `onDisconnect` fired exactly once (once-guard branch now directly covered). — every reviewer flagged this. The AC1 "error cause" test (`_statusServer(500)`) exercises the **non-2xx direct `connection.disconnect(error)`** path (http_agent.dart:247), *not* `ConnectionScope.track`'s `onError → disconnect(error); addError` branch (lifecycle.dart:129-132). That arm is the only path that both fires `onDisconnect` with a non-null cause **and** forwards the error so the run still surfaces it — it is load-bearing and has zero coverage. Spec Task 3 made it "and/or", so the AC is not violated, but it is the highest-value gap before the 4.10 ≥90% coverage gate. Fix: add a test driving a connected 200 stream that errors mid-stream (malformed `data:` JSON → `ProtocolError`, or an abrupt server close) and assert `onDisconnect` receives the stream error as cause, exactly once. Optionally tighten the existing throwing-observer test to assert `onDisconnect` fired exactly once (the once-guard no-op branch is currently only indirectly covered).

- [x] [Review][Patch] `onConnect ⇔ onDisconnect` pairing is enforced by laziness, not by construction (latent — not currently reachable) [packages/koel_http/lib/src/http_agent.dart:225-271] — **FIXED (documented, per "no just-in-case code")**: verified the band is unreachable today, so a `try/catch` would be dead code; instead added a precondition comment at the stream-build band in `_TransportTerminal.run` ("keep this band lazy if it ever grows; stream errors route through `track`'s `onError`") and a comment on `track`'s `onError` recording the error⇒done precondition it relies on (fire-before-forward so an error cause wins the once-guard; not closed there because every `async*`/`buildStage` upstream emits `done` after an error). — `connected()` fires `onConnect`; the dartdoc (lifecycle.dart:49-50) promises the pair is "Always paired one-to-one." Between `connected()` and the `yield* abortOnCancel(connection.track(events), …)` subscription sit `SseParser().parse()` + `.transform(chunksStage)` + `track()` + `abortOnCancel()`. **Verified: all four are lazy** (`parse` is `async*`, `chunksStage` is a `StreamTransformer`, both controllers build without subscribing), so **no synchronous throw exists in that band today** — the invariant holds. The finding is that it holds *by coincidence*: a future eager-throwing line added in that band would fire `onConnect` with no matching `onDisconnect`, silently breaking the contract DevTools (Epic 8) relies on. Related: `track`'s `onError` (lifecycle.dart:129-132) neither closes the controller nor cancels upstream — safe only because every real upstream (`async*`/`buildStage`) emits `done` after an error. Fix options (per koel's "explicit lifecycle > magic"): wrap the band in `try { … } catch (e) { connection.disconnect(e); rethrow; }` to make pairing true by construction, **or** add a one-line comment documenting the error⇒done / lazy-construction precondition the invariant rests on. Lean call given "no just-in-case code": the documenting comment is the minimal honest fix; the try/catch is defensible if the pairing guarantee is considered hard contract.

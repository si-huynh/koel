# Story 2.14: `KoelClient` + `ChatSession` 3-layer API + `runRaw` escape hatch

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **Dev agent:** this story touches `.dart` files, public-API design, `Stream`/`StreamController`/`StreamSubscription` lifecycle, broadcast semantics, and resource disposal. **Invoke `/agent-flutter-engineer` before producing any code** (per CLAUDE.md). This is the **capstone integration story of Epic 2** — it ends the 2.10/2.11/2.12/2.13 "ship the type, defer the wiring" deferral chain by wiring *every* prior kernel piece into the top-level surface. Four disciplines are load-bearing:
> 1. **The reducer fold lives in the apply stage as a side accumulation, NOT in a `ChatSession` post-pipeline `.map`.** This is forced by two independent sources: `apply_stage.dart:11-14` ("The fold is a **side accumulation** surfaced to `ChatSession.stream` as `ChatState` — it does **not** rewrite the event stream") and Addendum A.1 :45-48 (`runRaw` = "pipeline applied but **no reducer**"). The pipeline therefore carries a *per-session* apply stage that folds the reducer and pushes `ChatState` to the session's sink; `runRaw` runs the **same** pipeline with the **identity** apply stage. See §"The wiring map" — get this seam right and everything else falls out.
> 2. **`MockAgent` does NOT exist yet.** AC3 literally says `MockAgent.fromEvents(...)`, but `MockAgent` is **Story 3.1** in the **empty** `koel_test` package. **Do not import it, do not build it** (that is the wrong package + a future story). Use a **private inline `AbstractAgent` double** mirroring the established `test/agent/interceptor_test.dart` `_FixtureAgent` pattern. See §"The MockAgent trap".
> 3. **Three deferred-work hardening items become actionable the moment the reducer is wired** (deferred-work.md :162, :167, :171). A throwing custom `ErrorClassifier`, a throwing custom/`Composed` reducer, and an unguarded `buildStage.onEvent` are all latent hangs/escapes that 2.14 must close *because* 2.14 is the story that first puts a consumer-supplied reducer + classifier into the live path. See §"Closing the three deferred hardening items".
> 4. **No global mutable state** (AC4). Every per-run/per-session piece is instance-scoped; the only shared globals you touch (`chunksStage`/`verifyStage`/`transformStage`) are stateless transformers whose `buildStage` factory mints fresh per-listen state. Hold **zero** `static` mutable fields on `KoelClient`.

## Story

As a Flutter/Dart developer,
I want the top-level `KoelClient` non-singleton class wiring `AbstractAgent`, interceptor chain, subscribers, classifier, conflict resolver, backpressure policy, and `devtoolsBufferSize`, plus the `ChatSession` middle-layer API and `runRaw` power-user escape hatch,
so that the three-layer API surface from FR-A2 + FR-D3 is consumable end-to-end with a `MockAgent`.

### Review Findings (code review 2026-05-30)

All 4 ACs verified met, all 3 deferred hardening items closed, out-of-scope discipline held (572 tests green, analyze 0). The findings below are **lifecycle-robustness gaps in `ChatSession`** not exercised by any AC test — the root cause is that `ChatSession` has no reliable "a run is in flight" predicate (`_sub`/`_completer` are never nulled on completion), so concurrent `send`, mid-run `clear`, post-completion `cancel`, and post-`dispose` `send` all misbehave. **Resolution (2026-05-30): the maintainer deferred the entire session-lifecycle/concurrency cluster (D1 + the four patches below) to Epic 6 `KoelChatController` (story `6-1`), where session lifecycle is architecturally owned — Story 2.14 ships the 3-layer wiring as scoped. All five are recorded in `deferred-work.md`.**

- [x] [Review][Defer] **Concurrent / re-entrant `send()` corrupts the session** — a second `send()` before the first run finishes overwrites `_completer` (the first `send`'s future then completes on the *second* run's `onDone`/never — the awaiter hangs or resolves early) and overwrites `_sub` **without cancelling the prior subscription**, so two reducer folds race into one `_state` and the first run becomes uncancellable [chat_session.dart:496-552] [blind+edge] — deferred to Epic 6 `KoelChatController`: session lifecycle/concurrency is its territory
- [x] [Review][Defer] **`_sub`/`_completer` never nulled on completion — no in-flight predicate** (the cluster's root cause) [chat_session.dart:533,594-597] — deferred to Epic 6 `KoelChatController`
- [x] [Review][Defer] **`clear()` does not cancel the in-flight run** — `_emit(const ChatState())` resets state, but the live run's `reducingApplyStage` (seeded at send-time) keeps folding onto its captured copy and the next event's `onState`→`_emit` resurrects the cleared conversation [chat_session.dart:565-568] — deferred to Epic 6 `KoelChatController`
- [x] [Review][Defer] **`cancel()` after a run already finished flips `idle`→`cancelled`** — unconditional `_emit(copyWith(phase: cancelled))` broadcasts a wrong phase over a completed conversation; should no-op when no run is in flight [chat_session.dart:558-562] — deferred to Epic 6 `KoelChatController`

### What this story is, in one paragraph
You are shipping the **top of the three-layer API** (F-A2): `KoelClient` (layer-1 config + the `runRaw` layer-3 escape hatch) and `ChatSession` (layer-2 stateful chat). This is the **integration capstone of Epic 2** — every isolated piece shipped in 2.1–2.13 (`AbstractAgent`, `InterceptorChain`, `AgentSubscriber`, `ErrorClassifier`, the 4-stage pipeline, `DefaultChatStateReducer`, `LastWriterWinsResolver`, `SessionStorage`) gets wired into one consumable surface, and the four prior "ship the type, defer the wiring" deferrals (2.10/2.11/2.12/2.13) are paid off here. The data flow is fixed (architecture.md :1080-1087): `agent.run → interceptor chain → pipeline (chunks→verify→apply→transform) → subscribers fire → ChatSession.stream emits ChatState`. The single subtle seam is the **apply stage**: the reducer fold is a *side accumulation* inside it (surfaced as `ChatState` to `ChatSession.stream`) that leaves the event stream untouched — which is precisely why `runRaw` can run the *same* pipeline with the *identity* apply stage and get "no reducer". Get that seam right and the rest is lifecycle plumbing. [Source: addendum.md A.1 :29-89, F-A2; architecture.md :1062-1087, §4 :564-582; apply_stage.dart:5-22]

### The wiring map (the heart of this story)
Two consumers share one backbone; they differ only in the apply stage:

```
KoelClient._pipelined(input, {apply}):
    InterceptorChain(interceptors, agent, _safeClassifier).proceed(input)   // a FRESH chain per run
      → runPipeline(_, apply: apply ?? applyStage)                          // chunks → verify → apply → transform
                                                                            //   apply == identity  (runRaw)
                                                                            //   apply == reducingApplyStage(...)  (ChatSession)

runRaw(input)        = _pipelined(input).map((e){ _notify(e); return e; })  // layer 3: NO reducer, NO state, NO persistence
ChatSession.send()   = _pipelined(input, apply: reducingApplyStage(
                          reducer, initial: _state, onState: _emit, classifier))
                          .listen((e){ _notify(e); _eventsCtrl.add(e); }, onDone: _complete, onError: …)
```

- **`reducingApplyStage`** folds `reducer.reduce(_state, event)` per event, pushes the new `ChatState` to `_emit` (→ `_state` + the broadcast `ChatState` controller), and `out.add(event)` unchanged. It is the *only* place the reducer runs. `runRaw` uses the identity `applyStage` → no fold → no `ChatState`. **This is the decisive design fact**: `runRaw` = "pipeline applied but no reducer" (Addendum A.1 :47) is achievable *only* if the reducer is in a swappable apply stage, not bolted onto a post-pipeline `.map` in `ChatSession`. Do not fold the reducer in `ChatSession`'s `listen` callback — that would double-reduce or break `runRaw`'s contract.
- **Subscribers fire post-pipeline** via `_notify`, the same dispatcher in both paths. Under interceptor retry, the chain re-executes and subscribers see each attempt — duplicates by design (Addendum C.1 :528).
- **`_emit` vs subscriber firing ordering:** `_emit` runs *inside* the apply stage (stage 3); `_notify` runs in the terminal `listen` (after stage 4). So for a given event, `ChatState` updates a hair before subscribers fire. Both are post-verify/canonical; the ordering is immaterial to consumers and matches "subscribers observe what the consumer sees".

### `newSession` is synchronous → no auto-load (RESOLVED — Design Decision 2)
`newSession({String? threadId, ChatState? initial})` returns `ChatSession`, **not** `Future<ChatSession>` (Addendum A.1 :43). A synchronous return **cannot `await`** `SessionStorage.load` (which is `Future`-typed for the Epic 6 I/O adapters). Therefore `newSession` does **not** auto-load persisted state — `initial` is the only seed (defaults to `const ChatState()`). Resume is explicit: the consumer (or the Epic 6 `KoelChatController`) calls `sessionStorage.load(threadId)` and passes the result as `initial`. The round-trip test in Task 7 exercises exactly this (`persist()` → `load()` → `newSession(threadId: same, initial: loaded)`). This keeps `newSession` allocation-cheap and synchronous (cold-start path Story 2.15 benches). [Source: addendum.md A.1 :43, :242-245; session_storage.dart async-for-I/O rationale from 2.13]

### Broadcast streams do not replay (RESOLVED — Design Decision 3)
`ChatSession.stream` (`Stream<ChatState>`) and `events` (`Stream<AgUiEvent>`) are **broadcast** controllers (architecture §4 :570 — multiple UI widgets listen). A broadcast `StreamController` **does not buffer or replay**: a listener attached after an event was added never sees it. The idiom — pin it in the dartdoc — is `ValueListenable`-shaped: **read the `state` snapshot for "now", then `listen(stream)` for changes.** The `state` getter is the always-current `_state`. Do **not** reach for `asBroadcastStream()` on a single-subscription source or a `BehaviorSubject`-style replay (no `rxdart` dependency; architecture §4 :568-569 routes multi-consumer through the *designed* broadcast point, which is this controller). Guard `_stateCtrl.add` with `!_stateCtrl.isClosed` so a late `_emit` after `dispose` is a no-op, not a `Bad state: Cannot add event after closing`. [Source: architecture.md §4 :566-571; dart:async `StreamController.broadcast`]

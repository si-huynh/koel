**The five benchmarks already exist and already carry the gate logic.** Stories 2.15 (reducer, cold-start), 4.10 (sse-parse), and 6.8 (memory, jank) each shipped a `*_bench.dart` harness with a shared `recordOrGate` contract (`perf_baseline.dart`) that is *already* three-mode: record-baseline-when-absent / `KOEL_PERF_UPDATE` → write; `KOEL_PERF_GATE` → fail on > 10% regression; default local → log-and-pass (never flakes). **So 9.4 is not "write benchmarks" — it is "make the existing benchmarks gate-able and gated."** Three things stand between today and a live gate, and each is a documented hand-off to this story:

1. **The committed baselines are wrong-device.** All five `test/perf/baselines/*.json` hold **this dev machine's** numbers (macOS, `recorded_dart: 3.12.0`), captured single-run at sealing time. PRD §10.1 mandates each SLO be measured *"on the CI reference device profile."* A `KOEL_PERF_GATE` run on `ubuntu-latest` comparing CI numbers against macOS baselines is a cross-hardware comparison — meaningless and flaky (the same class of bug as the *Goldens are Linux-canonical* finding). **9.4 must (re)capture the five baselines on the reference device** via `KOEL_PERF_UPDATE` before wiring the gate (deferred-work.md:280, :284).
2. **Two benches are not yet gate-honest.** `reducer_bench` floors `elapsedMicroseconds` before dividing by 28 → on faster CI hardware a sub-µs sweep records **`0.0`**, and `value <= baseline*1.10` then always passes → a **silent no-op gate** (deferred-work.md:285). `chat_session_memory_bench` samples `ProcessInfo.currentRss` deltas whose run-to-run p99 swings **±88%** from GC nondeterminism → a naive single-sample > 10% hard-block **false-trips** (deferred-work.md:424). Both must be hardened so the gate *bites without flaking* — a gate that can't fail (or fails randomly) is worthless (the codegen-drift retro-D1 lesson 9.3 re-proved).
3. **The workflow + orchestrator + docs don't exist yet.** `perf-bench.yml` is the Epic-1 `echo "Wired in Epic 9"` placeholder; `tool/perf/run_benchmarks.dart` (architecture.md:738) is unbuilt; there is **no `BENCHMARKS.md`** at the repo root (architecture.md:721).

**Scope frame:** this is **tooling + CI + docs + test-harness hardening**, mirroring 9.3's shape. It adds **no new public symbol**, **no `lib/src/**` change**, and **no new workspace dependency** (the orchestrator is pure `dart:io`; `melos` is already a dev-dep; the bench files are `test/`). The only Dart edits are `tool/perf/run_benchmarks.dart` (new) and the two bench-harness hardenings under `test/perf/` (D3, D4) — neither touches a published surface, so `api-diff.yml` stays green.

## Dev Notes

### Locked decisions

- **D1 — Reference device = the GitHub `ubuntu-latest` hosted runner, pinned Flutter `3.44.0` / Dart `3.12.0`.** *(Parity decides — FYI→Si.)* PRD §10.1 mandates each SLO be measured *"on the CI reference device profile"* but never names the device; the architecture puts `perf-bench.yml` on the standard CI runner (architecture.md:730) and `BENCHMARKS.md` is *"reference device profile (per §10.1)"* (architecture.md:721). The only device that *runs the gate on every PR* is the `perf-bench.yml` runner — `ubuntu-latest` with the `.tool-versions` Flutter/Dart pins, identical to `api-diff.yml`/`ci.yml`'s lanes. So the reference device **is** that runner, and BENCHMARKS.md documents it as such. **Honest caveat (document it, don't hide it):** GitHub hosted runners are not a fixed CPU — successive jobs can land on different hardware generations, so absolute-µs metrics carry shared-runner jitter. The > 10% regression band (and N-3's wider band, D3) is what absorbs that jitter; the gate measures a *relative* regression against a baseline captured on the *same runner class*, which is the most stable contract available without a self-hosted fixed device. A dedicated/self-hosted fixed reference device is a possible post-1.0 hardening, not a v1.0.0 blocker (record as FYI). The PRD's original "Pixel 4a" device-class aspiration (review-rubric) is a *real-device* concern → D8.

- **D2 — Recapture all five baselines ON the reference device; do not keep the dev-macOS bytes.** The committed `test/perf/baselines/*.json` are this dev machine's single-run macOS captures (deferred-work.md:280 explicitly hands this to `9-4`: *"must (re)capture the canonical reference-device baselines via `KOEL_PERF_UPDATE` on the CI reference device before wiring `perf-bench.yml` to gate"*). A `KOEL_PERF_GATE` run on `ubuntu-latest` vs macOS baselines compares different hardware → false reds/greens.

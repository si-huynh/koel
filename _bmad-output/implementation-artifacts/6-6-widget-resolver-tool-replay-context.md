# Story 6.6: `WidgetResolver` + `ToolReplayContext` `InheritedWidget`

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Flutter developer,
I want `WidgetResolver` mapping tool-call name → Flutter Widget builder with `onUnknown` fallback, plus `ToolReplayContext` published via `InheritedWidget` so handlers consult it during DevTools replay,
so that generative UI on `TOOL_CALL_*` events composes safely with the DevTools replay path per FR-E2 + FR-F7.

## Context & scope (read first)

This is the **first Group-E generative-UI deliverable** and the **sixth symbol family** in `koel_flutter` (after `KoelChatController`, `KoelClientScope`, `HiveSessionStorage`, `SecureSessionStorage`, `MessageContentParser`/`MessageSegment`). It is **single-package** (`koel_flutter` only), **no new dependency** (`flutter` + `koel_core` are already deps — [pubspec.yaml](../../packages/koel_flutter/pubspec.yaml)), **no codegen**, **no `koel_core` change**. The whole job is two small files under a new `lib/src/generative_ui/` dir — a `WidgetResolver` (tool-name → `Widget` builder registry with an `onUnknown` fallback + a built-in `UnknownGenerativeUI` placeholder), and a `ToolReplayContext extends InheritedWidget` (a single `bool isReplaying` flag descendants read via `of`) — plus the barrel lines and Flutter widget tests.

**Three spec-reality gaps make this more than "look up a builder in a map." Resolve them exactly as the locked decisions say — do not re-derive from A.6 alone:**

1. **`ToolCallEvent` does not exist.** Addendum A.6 ([addendum.md:428-435](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L428)) and PRD F-E2 ([prd.md:171](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L171)) write the registry/`resolve` signature over a type named `ToolCallEvent` — but **no such type is defined anywhere in koel_core** (confirmed: the real tool-call events are `ToolCallStartEvent` / `ToolCallArgsEvent` / `ToolCallEndEvent` / `ToolCallResultEvent` / `ToolCallChunkEvent`, each `extends AgUiEvent`, with **no shared `ToolCallEvent` base** — [tool_call_events.dart](../../packages/koel_core/lib/src/event/tool_call_events.dart)). The epic's own BDD — the binding story contract — uses `ToolCallStartEvent(toolCallName: "chart")` ([epic-6:138](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L138)), and `ToolCallStartEvent` is the **only** tool-call event that carries `toolCallName` (the resolution key) alongside `toolCallId`/`parentMessageId`. PRD even marks the signature `[ASSUMPTION] — exact signature pending review` and flags it in the Anchors-to-revisit table ([prd.md:382](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L382)). **→ D1: use `ToolCallStartEvent`** (same "A.6 is illustrative shorthand" call as 6.5/D2).

2. **`ToolReplayContext.of` must NEVER throw** (the opposite of `KoelClientScope.of`). Per Addendum C.3 ([addendum.md:556-557](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L556)), handlers consult `if (ToolReplayContext.of(context).isReplaying) return;` **during normal live operation** — where there is no replay scope in the tree (the DevTools replay wrapper only exists in Epic 8 replay mode). A flag that crashed every live handler would be a footgun. **→ D4: `of` is total; absent ancestor → a const "live" default `isReplaying: false`.**

3. **`UnknownGenerativeUI` is named by the epic but absent from A.6's literal list.** The epic AC requires a *rendering* built-in fallback widget called `UnknownGenerativeUI` ([epic-6:135,144](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L135)); A.6 lists only `WidgetResolver`. **→ D3: ship `UnknownGenerativeUI` as a real public placeholder widget** — the one place this story *extends* A.6's headline list (epic-mandated, not gold-plating), in deliberate contrast to how 6.1–6.5 *trimmed* surface A.6 over-listed.

There is **no sealed type** in this story, so the `koel_lints` `exhaustive_switch_must_have_default` rule (6.5's whole second axis) is **irrelevant here** — do not write a `switch` over `AgUiEvent`/`ToolCallStartEvent` without `default:` and there is simply nothing to trip. Read **Dev Notes → Design decisions (D1–D8, locked)** before writing any code.

## Acceptance Criteria

1. **`WidgetResolver` shape matches Addendum A.6 over `ToolCallStartEvent` (AC source: [epic-6:132-135](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L132), [addendum A.6:428-435](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L428)).** `packages/koel_flutter/lib/src/generative_ui/widget_resolver.dart` exposes `class WidgetResolver` whose constructor is `WidgetResolver(this._registry, {this.onUnknown})` (A.6-exact — positional **private** `_registry` field + named optional `onUnknown`; D2), with `final Map<String, Widget Function(BuildContext, ToolCallStartEvent)> _registry` and `final Widget Function(BuildContext, ToolCallStartEvent)? onUnknown`. `Widget resolve(BuildContext context, ToolCallStartEvent toolCall)` returns the registered builder's widget for `toolCall.toolCallName`, else `onUnknown`'s widget, else a built-in `UnknownGenerativeUI` placeholder. The registry/`resolve`/`onUnknown` are typed over `ToolCallStartEvent`, **not** the non-existent `ToolCallEvent` (D1).

2. **A registered builder resolves and renders (AC source: [epic-6:137-140](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L137)).** Given a `WidgetResolver` constructed with `{'chart': (ctx, tc) => <a chart widget>}`, when `resolve(context, ToolCallStartEvent(toolCallId: 'c1', toolCallName: 'chart'))` runs, it returns exactly that chart widget, **and** a widget test pumping the resolved widget into a surface renders it with no exceptions (`tester.takeException()` is null; `find.byType(<chart widget>)` finds it).

3. **An unregistered name falls back (AC source: [epic-6:142-144](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L142)).** Given the same resolver, resolving `ToolCallStartEvent(toolCallName: 'unknown')`: (a) with **no** `onUnknown`, renders the built-in `UnknownGenerativeUI` (`find.byType(UnknownGenerativeUI)` finds it); (b) with an `onUnknown` builder supplied, renders **that** builder's widget instead (and `UnknownGenerativeUI` is absent). The fallback also fires when the name is registered to nothing — the lookup is `_registry[toolCall.toolCallName]`, total over any string.

4. **`ToolReplayContext` is a total, replay-safe `InheritedWidget` flag (AC source: [epic-6:146-149](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L146), [addendum C.3:556-557](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L556), [prd F-F7:183](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L183)).** `packages/koel_flutter/lib/src/generative_ui/tool_replay_context.dart` exposes `class ToolReplayContext extends InheritedWidget` with `final bool isReplaying` and `static ToolReplayContext of(BuildContext context)`. When a subtree is wrapped in `ToolReplayContext(isReplaying: true, child: …)`, a descendant's `ToolReplayContext.of(context).isReplaying` reads `true` (so a handler can early-return and skip side effects). When **no** `ToolReplayContext` ancestor exists, `of` returns a default with `isReplaying == false` and **does not throw** (D4) — the live-mode answer. `updateShouldNotify(old) => isReplaying != old.isReplaying` (D5).

5. **Barrel, dartdoc, gates, scope boundaries.** `lib/koel_flutter.dart` adds a new generative-UI banner exporting **exactly** `WidgetResolver`, `UnknownGenerativeUI`, and `ToolReplayContext` (nothing else — D7). Every public symbol carries contract-form dartdoc (NFR-16). **No new dependency** (`flutter` + `koel_core` only); `pubspec.lock` must not drift and the AI-5.9 pins (`analyzer 12.1.0` / `freezed 3.2.6-dev.1`) stay untouched (D6). `melos run analyze` (11 pkgs clean), `melos run test` (full sweep SUCCESS), `melos run format:check` (0 changed) all green. ## Dev Notes

### Design decisions (locked — implement as stated)

- **D1 — Registry/`resolve`/`onUnknown` are typed over `ToolCallStartEvent`, NOT the non-existent `ToolCallEvent`.** Addendum A.6 ([line 431-434](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L431)) and PRD F-E2 ([line 171](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L171)) write the signature over `ToolCallEvent` — but **no such type exists** in koel_core. The concrete tool-call events ([tool_call_events.dart](../../packages/koel_core/lib/src/event/tool_call_events.dart)) are `ToolCallStartEvent` / `ToolCallArgsEvent` / `ToolCallEndEvent` / `ToolCallResultEvent` / `ToolCallChunkEvent`, each a direct `@freezed ... extends AgUiEvent` part — there is **no shared `ToolCallEvent` superclass**. Of these, only `ToolCallStartEvent` (and the convenience pre-expansion `ToolCallChunkEvent`) carries `toolCallName`, and the resolver's whole job is name → widget, so the event it receives must carry the name. The epic's BDD — the **binding** story contract — names `ToolCallStartEvent(toolCallName: "chart")` explicitly ([epic-6:138](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L138)). PRD marks F-E2's signature `[ASSUMPTION] — exact signature pending review; intent locked` ([prd.md:171](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L171)) and lists it in the Anchors-to-revisit table ([prd.md:382](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L382)). **Parity + source-evidence decide:** `ToolCallStartEvent`. This is the same "A.6 writes illustrative shorthand; the real, faithful type wins" call as 6.5/D2 (`class` vs `final class`). `ToolCallStartEvent` is already public via the `koel_core` barrel (`export 'src/event/ag_ui_event.dart'`, which `part`s in every concrete subtype — [koel_core.dart:42](../../packages/koel_core/lib/koel_core.dart#L42)).

- **D2 — Honor A.6's exact constructor: positional private `_registry` + named `onUnknown`.** A.6 ([line 429](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L429)) writes `WidgetResolver(this._registry, {this.onUnknown})` — the registry is a **private** field (`_registry`) initialized from a **positional required** parameter, and `onUnknown` is a **named optional** field. Implement that signature verbatim (do not "improve" it to a named `registry:` parameter — A.6 is the pinned surface, and a positional map at the call site reads fine: `WidgetResolver({'chart': …}, onUnknown: …)`). Keep the **raw inline** function type `Widget Function(BuildContext, ToolCallStartEvent)` in the public surface to match A.6 literally; a `private` typedef (`typedef _GenUiBuilder = …`) is acceptable for readability **only if it never appears in a public signature** (it would, via `resolve`/`onUnknown`, so in practice keep it inline — D7).

- **D3 — `UnknownGenerativeUI` is a real, public placeholder widget — the one place this story extends A.6's literal list.** A.6 ([428-435](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L428)) lists only `WidgetResolver`, but the epic AC1/AC3 ([epic-6:135,144](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L135)) name `UnknownGenerativeUI` as the built-in fallback that **renders**, and PRD F-E2/§9 call it the "consumer-overridable placeholder" ([prd.md:171,404](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L171)). It is a **user-visible rendered widget** (not an internal helper), so it is public, barrel-exported, and referenceable in tests (`find.byType(UnknownGenerativeUI)`). **This is additive-but-epic-mandated, not gold-plating** — the deliberate contrast with 6.1–6.5, which *trimmed* symbols A.6 over-listed (6.1 dropped `tools`, 6.2 omitted `maybeOf`, 6.3 no `open`, 6.4 no `clearAll`, 6.5 no inline-code segment). Here the binding spec (epic AC) *adds* a symbol A.6's headline entry omitted. Keep it minimal: `const UnknownGenerativeUI({required this.toolCallName, super.key})`, one `final String toolCallName`, a `build` over `package:flutter/widgets.dart` only (no Material/Cupertino dependency — it must render under any host app; the richer themed primitives are `koel_widgets`, Epic 7). The placeholder surfaces the unhandled `toolCallName` (useful, debuggable) — nothing more.

- **D4 — `ToolReplayContext.of` is TOTAL (never throws); absent ancestor → a const "live" default `isReplaying: false`.** This is the **deliberate opposite** of `KoelClientScope.of`, which throws a `FlutterError` ([koel_client_scope.dart:44-61](../../packages/koel_flutter/lib/src/scope/koel_client_scope.dart#L44)) because a missing client *is* a programming error. Here the flag is consulted by tool handlers **during normal live operation** (`if (ToolReplayContext.of(context).isReplaying) return;` — [addendum C.3:556](../planning-artifacts/prds/prd-koel-2026-05-27/addendum.md#L556)), and in live mode **no `ToolReplayContext` is mounted** (the DevTools replay wrapper exists only in Epic 8 replay mode — C.3:557 "Replay-unaware tool handlers execute normally during live mode"). A flag that crashed every live handler would be a footgun ("design for what users *can't* misuse," CLAUDE.md). So `of` returns a `static const ToolReplayContext _live = ToolReplayContext._live();` (a private `const ToolReplayContext._live() : isReplaying = false, super(child: const SizedBox.shrink());`) when there is no ancestor — a **detached value holder**, never inserted in the tree, read only for `.isReplaying`. `SizedBox` is from `package:flutter/widgets.dart` (already imported); `const SizedBox.shrink()` is a const expression, so the whole default is a compile-time constant.

- **D5 — `of` reads WITHOUT subscribing (`getInheritedWidgetOfExactType`); field is `isReplaying`.** The flag is read **imperatively** inside tool-handler callbacks, not reactively inside a `build` method. `context.dependOnInheritedWidgetOfExactType<T>()` outside `build` is a footgun (registers a dependency on an element that may rebuild for unrelated reasons, and "depend outside build" is discouraged). `context.getInheritedWidgetOfExactType<ToolReplayContext>()` (Flutter framework API, present in the SDK ≥3.38 this package targets — [pubspec.yaml](../../packages/koel_flutter/pubspec.yaml)) reads the **current** inherited value with **no** dependency — the correct API for an imperative flag. Still implement `updateShouldNotify(old) => isReplaying != old.isReplaying` (correct value semantics), so a consumer who genuinely wants reactive rebuilds on replay-toggle can `dependOnInheritedWidgetOfExactType<ToolReplayContext>()` themselves. **Field name is `isReplaying`** — epic AC4 ([epic-6:148](../planning-artifacts/epics/epic-6-flutter-glue-persistence-koelflutter.md#L148)) and Addendum C.3 both say `isReplaying`; PRD F-F7's looser `replayed: true` ([prd.md:183](../planning-artifacts/prds/prd-koel-2026-05-27/prd.md#L183)) is the earlier, less-canonical phrasing — the addendum + epic win (parity-by-canonicity).

- **D6 — No new dependency; no sealed type; no `koel_lints` concern.** `WidgetResolver` and `ToolReplayContext` are plain Flutter classes over `package:flutter/widgets.dart` + `koel_core`'s `ToolCallStartEvent` — both already deps. Add **no** package. `pubspec.yaml` untouched, `pubspec.lock` must not drift, AI-5.9 pins (`analyzer 12.1.0` / `freezed 3.2.6-dev.1`) hold trivially (parity with 6.5/D5). Neither type is a `sealed` union and the story writes no `switch` over a sealed type, so the `exhaustive_switch_must_have_default` rule that dominated 6.5 is **not in play** — nothing to register, nothing to trip, no integration test for it.

- **D7 — A.6-exact + epic-exact surface.** Public surface this story adds: `WidgetResolver` (constructor, `resolve`, `onUnknown` field), `UnknownGenerativeUI` (constructor, `toolCallName` field — D3), `ToolReplayContext` (constructor, `isReplaying` field, `of`). **Nothing else** — no registry-mutation API (`register`/`unregister`), no `resolveByName(String)` overload, no `ToolCallEvent` typedef, no replay-`enum`, no `maybeOf`. Same discipline as 6.1–6.5. `_registry` stays private (A.6, D2).

- **D8 — Tests are Flutter widget tests (`flutter_test` + `WidgetTester.pumpWidget`), mirroring `koel_client_scope_test.dart`.** Both new types are Flutter-coupled (`Widget`/`BuildContext`/`InheritedWidget`), so unit-only tests can't exercise `of`/rendering — use `testWidgets`. `tool/test_package.sh` already routes `koel_flutter` → `flutter test` (landed in 6.1), so no harness change. Coverage gate → 6.8, six-platform CI → 6.7 (deferred, parity with 6.3/6.4/6.5).

### `InheritedWidget` pattern reference (the layout to mirror — and where to diverge)

`KoelClientScope` ([koel_client_scope.dart](../../packages/koel_flutter/lib/src/scope/koel_client_scope.dart)) is the template: `extends InheritedWidget`, `const` constructor with `required super.child`, a `static … of(BuildContext)`, and `updateShouldNotify`. **Two deliberate divergences for `ToolReplayContext`** (do not copy these from the scope): (1) `of` is **total** — no `FlutterError` on a missing ancestor; it returns the const `_live` default instead (D4). (2) `of` uses **`getInheritedWidgetOfExactType`** (non-subscribing), not `dependOnInheritedWidgetOfExactType` (D5). The constructor, `final` field, and `updateShouldNotify` shapes are otherwise identical in spirit. The `_Swapper` test harness in [koel_client_scope_test.dart:105-132](../../packages/koel_flutter/test/scope/koel_client_scope_test.dart#L105) is the model for the `updateShouldNotify` flip test (Task 4).

### `ToolCallStartEvent` (the resolve input — context only, nothing to change)

### Dismissed (9) — rationale

- **`of` uses `getInheritedWidgetOfExactType` + defines `updateShouldNotify` ⇒ "stale/dead-code bug" (Blind+Edge, flagged High)** — This is **locked decision D5**, confirmed PASS by the Acceptance Auditor. The flag is read *imperatively* in handler callbacks (`if (ToolReplayContext.of(context).isReplaying) return;`), where `dependOnInheritedWidgetOfExactType` outside `build` is itself the footgun. `updateShouldNotify` is a deliberate affordance so a consumer who *does* read in `build` can opt into reactivity via explicit `dependOn…` — exercised by the AC4 flip test. Not dead, by design. (The hunters lacked spec context.)
- **Registry held by reference, not defensively copied (Blind+Edge)** — D2 locks the A.6-exact `WidgetResolver(this._registry, …)` initializing-formal verbatim ("do not improve it"); the documented usage passes an inline literal (no external reference to mutate). Parity decides.
- **`_live` const default is a never-mounted `InheritedWidget` (Blind+Edge)** — D4 by design: a detached value holder, private, returned only for `.isReplaying`. Misuse requires future code to mount a private symbol.
- **`of` silently returns `_live` instead of warning on a missing ancestor (Edge)** — D4 is exactly this: absent ancestor *is* live mode (the common case); a diagnostic would fire on every live handler — the deliberate opposite of `KoelClientScope.of`.
- **`UnknownGenerativeUI` bare `Text` needs ambient `Directionality` (Blind)** — Any real host (`WidgetsApp`/`MaterialApp`) provides one; the doc claims "renders under any host *app*," which is accurate. The test's explicit `Directionality` wrap is the standard widget-test idiom.
- **Duplicate tool names → last-write-wins (Edge)** — Standard Dart `Map` semantics; literal duplicate keys are caught by the analyzer.
- **Empty/whitespace `toolCallName` → blank label (Edge)** — Cosmetic, malformed-upstream input; renders safely (no crash).
- **Empty registry / positional-map discoverability (Blind)** — Empty registry is valid and total via fallback; positional map is the D2-locked A.6 surface.
- **`updateShouldNotify` covariant-signature note (Edge)** — Informational; matches `InheritedWidget` base, no defect.
